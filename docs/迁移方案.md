## 一、结论

**可行。** 且这次迁移的条件比一般情况好得多，原因有三：

1. **核心层零宿主耦合。** `src/core/` 9 个文件、2,476 行中，1,978 行（`caldav` / `ics` / `sync` / `store` / `date` / `types` / `reminder`）完全没有 `import "siyuan"`，也没有任何反向依赖 UI 层。CalDAV 协议交互、iCal 解析与序列化、RRULE 展开、EXDATE、RECURRENT-ID 覆盖、双向同步引擎——这些最难写的部分可以**整块搬走，一行不改**。
2. **零运行时第三方依赖。** 源项目 `package.json` 的依赖全在 `devDependencies`（typescript / vite / jsdom / jszip），`jszip` 只用于打包脚本。移植不会引入依赖地狱。
3. **网络层反而变简单。** `http.ts` 里最麻烦的部分是思源内核 `forwardProxy` 的种种约定（headers 必须是单键对象数组、`payloadEncoding: base64` 强制、`contentType` 独立字段、body 必须 base64 编码）。Obsidian 的 `requestUrl()` 桌面端走 Electron、移动端走 Capacitor 原生 HTTP，**天然无 CORS**，这一整段连同"直连被拦后回退代理"的兜底逻辑都可以删掉。

**必须重写的是宿主适配层：** 入口 `index.ts`（957 行）、UI 层 `ui/*`（4,224 行）、以及 CSS 里对思源 Dialog 结构的适配。

**预期代码复用率：约 35%**（core 层 2,476 行），另需新写约 4,000 行（以视图与设置为主）。

### 2.3 库内已有方案对比（决定"值不值得做"）

你的 Obsidian 库 `D:\Obsidian\Obsidian` 里已装了三个日历类插件，逐个查过实现：

| 插件 | 规模 | 实现方式 | 事件 (VEVENT) | 待办 (VTODO) |
| --- | --- | --- | --- | --- |
| **Ogenda** 1.3.6（已启用） | 214 KB | 自研 CalDAV（含 `ical.js`） | ✅ 完整 | ❌ **无** |
| **daydav** 1.0.3 | 101 KB | 借 Full Calendar Remastered 的 token | ✅ | ❌ |
| **Full Calendar Remastered** 0.13.6 | 3.3 MB | 自研 CalDAV，`requestUrl` + PROPFIND/REPORT | ✅ 完整 | 侧重展示 |

**关键发现：Ogenda 生成 ICS 时硬编码 `BEGIN:VEVENT`**，业务代码里 `vtodo` 仅在 `ical.js` 的组件表里出现过一次——它有解析能力，但没有任务功能。你的 `data.json` 里 `caldavUrl/User/Pass` 目前全是空的。

**结论：现有三个方案在"待办任务的双向同步"上都是空白。** 而你的思源插件从名称（"CalDAV日历任务"）到数据模型（`kind: "event" | "todo"`、`priority`、`status`、`percent`、`completedAt`、任务视图、待办到期滚动）都是围绕事件 + 任务双轨设计的。**这就是迁移的核心增量价值，不是重复造轮子。**

顺带一个技术红利：FCR 用 `requestUrl` 跑 `PROPFIND` / `REPORT` / `Depth` 头，这是 Obsidian 平台**能否**做 CalDAV 的最强实证——库内就有活例子，方案里的网络层假设由此成立。

## 六、关键改造点详解

### 6.1 网络层：删除代理通道

源 `http.ts` 的核心是双通道（内核代理 + 浏览器直连）加自动回退。移植后只保留一个通道：

```ts
// src/obs/http-adapter.ts（新增）
import { requestUrl } from "obsidian";

export async function rawRequest(url: string, opts: HttpOptions): Promise<HttpResult> {
  const t0 = Date.now();
  const res = await requestUrl({
    url,
    method: opts.method || "GET",
    headers: opts.headers,
    body: opts.body,
    throw: false,          // 由上层按 status 判定，不抛异常
  });
  return {
    status: res.status,
    headers: normalizeHeaders(res.headers),   // 小写键
    body: res.text,
    elapsedMs: Date.now() - t0,
    via: "direct",
  };
}
```

`httpRequest(url, opts, channel, auth)` 的对外签名保持不变，`channel` 参数保留但恒为 `"direct"`，这样 `caldav.ts` / `sync.ts` 一行都不用动。

**必须实测验证的点**（FCR 的用法提供了信心，但不能替代自测）：

| 验证项 | 方法 | 预期 |
| --- | --- | --- |
| `PROPFIND` 自定义方法 | 对 Radicale 发起深度 1 的 PROPFIND | 207 Multi-Status |
| `Depth` 自定义头是否透传 | 同上，检查返回条目层级 | 与桌面 curl 结果一致 |
| `Authorization: Basic` | 检查能否通过鉴权 | 非 401 |
| `REPORT` + calendar-query | 拉取时间区间内事件与待办 | 正确返回 VEVENT / VTODO |
| `PUT` / `DELETE` | 新建与删除条目 | 201 / 204 |
| 移动端（如需要） | 同上，用 `http://` 明文地址 | 注意明文限制 |

> **已知需留意**：`requestUrl` 的 `body` 只接受字符串（与思源 base64 约定不同，反而更简单）；响应头是普通对象且键名可能大小写不一，原 `normalizeHeaders()` 逻辑要保留。

### 6.2 凭据存储：保留"密钥随数据走"的设计

源 `secret.ts` 的设计经过实战打磨，**建议整体保留其思路**：

- `enc:v3:` 格式下，主密钥（keyring）**随插件数据一起持久化**，理由在源码注释里写得很清楚：思源云同步会带走 petal 目录的数据，但不带 `conf/`；若密钥来自 `conf/`，就会出现"手机写入 → PC 解不开 → PC 回写空密码 → 同步回手机也丢"的双向覆盖。
- `localStorage` 只是**本机镜像**，权威副本是随数据走的 keyring。
- `store.ts` 的 `persist()` 严格区分"用户本来没密码"与"密钥未就绪导致解不开"——后者必须把原始密文 `rawCipher` 原样写回，绝不写空串。

**移植后的差异**：

| 项 | 思源 | Obsidian |
| --- | --- | --- |
| 权威副本 | petal 目录（云同步带走） | `data.json`（若开 Obsidian Sync 则同步插件数据） |
| 本机镜像 | `localStorage` | 保留 `localStorage` 作为 best-effort，失败不致命 |
| `seed`（v2 兼容） | `conf.system.id + 工作空间路径` | 传空串（新仓库无 v2 历史密文，等价于直接跳过兼容分支） |
| 加密算法 | AES-GCM 256 + WebCrypto | **完全一致，无需改动** |

**安全语义提示**：`data.json` 是明文 JSON，keyring 在其中以明文 base64 存在——这与思源 petal 同级别（源码注释也承认"等价于本地混淆"）。桌面端若要更强保护，可用 Electron `safeStorage` 包裹 keyring，**但代价是密钥不再随数据走，跨设备会重现丢密码问题**。建议保持原设计。

### 6.3 视图承载：从 Dock + Tab 双承载到单 ItemView

思源版本的形态：左侧 Dock（精简导航：视图切换 + 设置）+ 主窗口页签（完整日历）。移动端因为"`addTab` / `openTab` 是空实现且没有页签栏"，额外用全屏 `Dialog` 承载同一套 `renderPanel`——由此衍生出 `mobile-layers.ts`（192 行）那套复杂的层级管理。

**Obsidian 不需要这套分支**：`ItemView` 在桌面端可停靠左右侧栏，移动端同样支持侧栏与视图打开，一套代码两端通用。

```ts
export const VIEW_TYPE_CALDAV = "caldav-main-view";

export class CalDavView extends ItemView {
  getViewType() { return VIEW_TYPE_CALDAV; }
  getDisplayText() { return "CalDAV 日历任务"; }
  getIcon() { return "calendar-check"; }
  async onOpen() { renderPanel(this.contentEl, this.plugin.createCtx()); }
  async onClose() { /* 清理订阅 */ }
}
```

入口注册：

```ts
this.registerView(VIEW_TYPE_CALDAV, (leaf) => new CalDavView(leaf, this));
this.addRibbonIcon("calendar-check", "打开 CalDAV 日历任务", () => this.activateView());
this.addCommand({ id: "open-caldav-panel", name: "打开日历任务面板", callback: () => this.activateView() });
```

`panel.ts` 的 1,337 行里，`renderPanel(root, ctx)` 的渲染与事件绑定逻辑**大部分可复用**——它操作的是自研的 `.caldav-*` DOM 结构与 `PanelCtx` 上下文，与宿主无关。真正要改的是上下文注入（`PanelCtx`）和几个调用思源 API 的出口（打开设置、通知）。

### 6.4 设置界面

思源版是自定义 Dialog（379 行）。Obsidian 改用 `PluginSettingTab` + `Setting` API，这部分是纯重写，但也是最标准、最没风险的一块：

```ts
class CalDavSettingTab extends PluginSettingTab {
  display() {
    const { containerEl } = this;
    containerEl.empty();
    new Setting(containerEl)
      .setName("服务器地址")
      .setDesc("CalDAV 根地址，如 http://192.168.1.x:5232/")
      .addText(t => t.setValue(s.serverUrl).onChange(async v => { s.serverUrl = v; ... }));
    // 用户名 / 密码（password）、日历勾选列表、同步间隔、提醒开关……
  }
}
```

需要注意的能力差异：思源版设置里有**日历列表拉取与逐个勾选**（含 `eventColor` / `todoColor` 分色），要在 `display()` 里动态渲染，Obsidian 的 `Setting` 支持动态增删，实现无碍。

### 6.5 日记集成

`insertTodayToDiary()` 现在依赖思源内核 API：`/api/query/sql` 找日记文档 → `/api/filetree/createDocWithMd` 建文档 → `/api/block/insertBlock` 插入 → `/api/block/deleteBlock` 清理旧小节。

Obsidian 侧对应改写：

| 原逻辑 | Obsidian |
| --- | --- |
| SQL 查日记文档 | `vault.getAbstractFileByPath(dailyFolder + "/" + today + ".md")` |
| 日记目录来源 | 读核心插件 daily-notes 配置（你的库当前是 `DailyNotes`） |
| 创建文档 | `vault.create(path, "")` |
| 插入内容 | `vault.process(file, (data) => ...)` |
| 替换已有小节 | 按 `DIARY_SECTION_TITLE` 标记做正则替换，逻辑原样保留 |
| 打开文档 | `workspace.getLeaf(false).openFile(file)` |

> 你的库里 `DailyNotes` 目录和 `2026-09-25.md` 都已存在，接入成本低。
> 注意一个语义差异：思源按块 ID 定位与删除，Obsidian 是纯文本 Markdown——原来靠块 ID 做的"重复点击替换而非追加"，要改为按小节标题匹配，源码里 `DIARY_SECTION_TITLE` 这个常量的设计意图正是为了这个，可以直接沿用。

### 6.6 移除的思源专有逻辑

| 项 | 说明 |
| --- | --- |
| `setDirectFallbackToProxy(isMobile())` | 移动端 WebView 拦明文/跨域直连的兜底，Obsidian 无此问题 |
| 内核代理的 3 条约定 | `headers` 单键对象数组、`payloadEncoding: base64`、`contentType` 独立字段——全部作废 |
| `DOCK_TYPE` / `TAB_TYPE` 常量 | 思源用于记账侧栏位置与已打开模型，Obsidian 无对应概念 |
| `mobile-layers.ts` | Dialog 异步销毁 + 遮罩层级的移动端问题，Obsidian Modal 无此问题 |
| `dialog-resize.ts` | 思源 Dialog 不带缩放，Obsidian 不需要 |
| 数据文件迁移逻辑 | `LEGACY_DATA_FILE` / `STALE_DATA_FILES` 是思源侧的历史包袱，Obsidian 版是全新仓库，无需背负 |

**保留的一项**：`DATA_FILE` 那份"带 `.json` 后缀便于直接查看"的思路，在 Obsidian 里天然成立（就是 `data.json`）。

### 实施中做出的两处设计调整

**① 网络层改为「注入式传输」而非直接 import 宿主**

方案原文写的是 `core/http.ts` 直接 `import { requestUrl } from "obsidian"`。实施时改为：

```ts
// core/http.ts —— 不 import 任何宿主模块
export type Transport = (url: string, opts: HttpOptions) => Promise<HttpResult>;
export function setTransport(t: Transport | null): void;
```

由入口 `onload()` 注入 `obs/http-transport.ts` 里的 `obsidianTransport`。

这样做的原因：源项目的 `test/*.test.mjs` 全在 Node 下直接跑 core 层，若此处硬编码 `import "obsidian"`，将来搬测试会在缺少宿主模块时失败。改注入后，Node 环境自动回退全局 `fetch`，**core 层「零宿主依赖」的分层约定得以完整保持**。

**② `PanelCtx` / `ViewMode` 类型抽到独立文件**

原定义在 `ui/panel.ts` 内，导致 `view-common.ts` 为了拿一个类型不得不 import 整个面板实现（而 panel 又反向依赖 view-month/week/year/task），形成类型层面的环。移植时抽出为 `src/ui/panel-ctx.ts`，视图模块只依赖类型文件。

**③ 一个共享常量文件**

`VIEW_TYPE_CALDAV` 同时被入口（注册视图）与视图模块（声明类型）使用，定义在 `main.ts` 会形成 `main.ts ↔ ui/main-view.ts` 的循环 import；打包成 CJS 后循环链上取到的可能为 `undefined`，表现为「视图注册成功但打不开」。故抽到 `src/constants.ts`。

### 构建环境的两个坑（新机器复现时注意）

**① esbuild 平台二进制装不上**

`npm install` 在本机会卡在 esbuild 的 postinstall —— 它要 spawn node 验证版本，报 `EBUSY`；换 npmmirror 镜像重装同样超时。网络与文件锁双重原因。

解决：直接从 SiYuan 项目复用 —— 后者经 Vite 依赖已装好完整的 `esbuild` + `@esbuild/win32-x64`：

```bash
rm -rf node_modules/esbuild node_modules/@esbuild
cp -r ../SiYuan/node_modules/esbuild node_modules/esbuild
cp -r ../SiYuan/node_modules/@esbuild node_modules/@esbuild
```

并把 `package.json` 的 esbuild 版本对齐为 `^0.21.5`（与 SiYuan 一致，避免版本校验失败）。
**注意**：`@esbuild/win32-x64` 是平台相关包，换机器时需按目标平台重新获取。

**② `package.json` 不能写 `"type": "module"`**

Obsidian 的 `main.js` 必须是 CommonJS。若 `package.json` 声明 `"type": "module"`，Node 会按扩展名把 `main.js` 当作 ESM，冒烟测试直接报 `module is not defined in ES module scope`。

而本项目里 esbuild 配置与部署脚本都是 `.mjs` 后缀 —— **`.mjs` 本身就表示 ESM，不需要 `type: module`**。已移除该字段。

### 关键改造

**① `Dialog` → `Modal` 的映射差异**

| 思源 `Dialog` | Obsidian `Modal` |
| --- | --- |
| `new Dialog({ title, content, width, height })` | `class X extends Modal` + `onOpen()` |
| `dialog.element.querySelector(...)` | `this.contentEl` / `this.modalEl` |
| 构造函数传 `width` / `height` | 走 CSS（`.modal.caldav-dialog`） |
| `dialog.destroy()` | `this.close()` |
| `containerClassName` | `this.modalEl.addClass(...)` |
| `destroyCallback` | `onClose()` |

- `app: App` —— Obsidian 的 `Modal` 构造函数要求显式传入 app，思源的 `Dialog` 自带全局上下文

**③ 视图承载合并**

原思源版是 Dock（240px 精简导航）+ 主窗口页签（完整面板）双承载。Obsidian 侧栏寸土寸金，故合并为单 `ItemView`：顶部宿主工具条（同步 / 插入日记 / 设置）+ 主体 `renderPanel`。

| 思源通道 | Obsidian |
| --- | --- |
| `showReminderToast`（自研浮层，带「打开」「稍后提醒」） | **保留**（零宿主依赖） |

### 值得记下的教训：**迁移 CSS 时，类名本身也是接口**

原 CSS 里的 `.caldav-settings` 不只是一个命名空间，它携带了思源 Dialog 的布局契约（固定高度 + 内部滚动容器）。复用类名等于继承这份契约；而新宿主（Obsidian 的 `PluginSettingTab`）是自然流式布局，契约不匹配，表现就是「内容被裁掉」。

同类风险点还有 `.caldav-editor`、`.caldav-catmgr`（同一选择器组）—— 前两者在 Obsidian 下由 `Modal` 承载，已在 `.modal.caldav-dialog .modal-content` 的规则里单独接管布局，不依赖原契约。

**推论**：后续若再往 Obsidian 的**非 Modal** 容器里放这些类（例如把某个面板嵌进主界面），需先确认该类是否绑定了宿主布局契约。

### 续：视图位置的完整修复

上一次只改了 `activateView()`，实测**未生效** —— 面板依旧在右侧栏。

根因：Obsidian 把视图位置持久化在 `.obsidian/workspace.json`，重启后按记录恢复。`activateView()` 只在「点击 Ribbon 图标」时触发，用户不点就永远不会迁移；而用户以为改完代码重启就好，于是看到"没修"。

完整修复（三处）：

1. **加载时主动迁移** —— `onLayoutReady` 里调用 `ensureViewPlacement()`：检测到有视图遗留在侧栏就 detach 掉、在主区域重开。这一步不再依赖用户操作。
2. **只迁一次** —— 用 `viewPlacedInMain` 持久化标记。否则用户哪天主动把面板拖回侧栏，重启又会被强行搬走。
3. **把选择权交回用户** —— 新增命令「在右侧栏打开日历任务」，`activateView(mode)` 支持 `main` / `right` 两个目标位置。

顺带修正一处行为：`activateView` 现在会先查目标位置是否已有实例，有则聚焦；没有才清掉其它位置的实例再重开 —— 避免同一视图存在多份。

> **教训**：涉及宿主**持久化状态**的改动（视图位置、面板布局、标签顺序），光改"创建/打开"的代码路径不够。宿主会在下次启动时按存档恢复，必须有一条**迁移路径**主动纠正存量状态，并用标记保证幂等。

## 十七、Dock 迁入右侧栏 + 单击/双击语义改造（2026-09-29）

### 1. Dock 视图迁入右侧栏

原思源版是「左侧 Dock（240px 精简导航）+ 主窗口页签（完整日历）」双承载。Obsidian 版对应为：

| 组件 | 承载位置 | 视图类型 |
| --- | --- | --- |
| 完整日历面板（`renderPanel`） | **中间主区域** | `caldav-main-view` |
| Dock 精简导航（`renderDockPanel`） | **右侧栏** | `caldav-dock-view`（本次新增） |

Dock 本体零宿主依赖，**从思源直接复用**：品牌栏、新增/排序下拉、日历/任务视图切换、刷新、筛选下拉、分类筛选弹层、搜索框、条目列表、同步状态一应俱全，本轮只写了 `ui/dock-view.ts` 这个 ItemView 外壳。

首次加载后**自动打开一次**（`dockAutoOpened` 持久化标记）—— Dock 是插件的主要入口，升级后应让用户立刻看到它；但主动关掉后不该每次加载又弹回来，故只做一次，之后交给命令「打开日历任务管理（右侧栏）」或拖拽。

### 2. 单击 / 双击语义改造

| 操作 | 原行为 | 新行为 |
| --- | --- | --- |
| 单击条目 | 打开编辑器 | 右侧栏列出该条目**所在格子**的当日清单 |
| 双击条目 | ——（原单击即编辑） | 打开编辑器 |
| 单击日历格子 | ——（无响应） | 右侧栏列出该日清单 |

实现要点：

- 事件委托只有一个 `click` handler，用 **`ev.detail >= 2`** 判定双击，不额外挂 `dblclick`。
- 日期取**用户实际点中的那个格子**（`closest("[data-day]")`）而不是条目自身的 `start` —— 同一条重复日程会出现在多个格子里，用 `start` 会对不上用户看到的那个。
- 月/周/年视图的格子都带 `data-day`，一套逻辑覆盖三种视图。

### 3. 两个视图之间怎么通信

主面板与 Dock 是两个**独立的 ItemView 实例**，互不持有引用，故走 `document` 事件总线（与既有的 `notifyViewChange` 同一套写法）：

| 方向 | 通道 | 用途 |
| --- | --- | --- |
| 主面板 → Dock | `FOCUS_DATE_EVENT`（`notifyFocusDate(date)`） | 单击格子/条目后让 Dock 切到该日清单 |
| Dock → 主面板 | `activateView("main", viewMode)` | Dock 的「日历视图 / 任务视图」按钮切换主面板 |

Dock 侧新增 `focusDate` 状态，**优先于** `dockFilter`：聚焦时下拉文案显示该日期（用户一眼看出列表为什么变了），且不点亮任何预设筛选项；用户一旦选择预设筛选即清除该状态。

补的一个交互缺口：单击格子时若 Dock 还没打开，**自动打开它** —— 否则用户点了一下什么都不会发生，像是坏了。这里用原生 `addEventListener` 而非 `this.registerDomEvent`，因为后者的类型签名限定在标准事件名（`keyof DocumentEventMap`）内，自定义事件名过不了类型检查。

### 4. 选中态高亮（补充）

右侧栏在这里的角色相当于主面板的「属性面板」—— 既然如此，主面板必须能看出当前选中的是哪一格，否则点完就对不上号。

- `selectedDay` 状态 + `.is-selected` 类，样式 `outline: 2px solid var(--caldav-accent)`。
  用 outline 而非 border/background：**outline 不参与布局**，格子尺寸不会跳动。
- 一套选择器覆盖四种视图 —— 月（`.cal-month-cell`）、周（`.cal-wk-col` / `.cal-wk-dayhead`）、
  年（`.cal-year-cell`）的共同点是都带 `data-day`。
- **视图切换会重建 DOM，故在 `renderView` 末尾统一恢复选中态**，而不是只在点击时标一次。
- 月/年视图里相邻月份的补白格子（`is-out`）可能与当前月同日，不参与高亮。

## 十八、浮层定位与配色修复（2026-09-30）

雄哥实测报的两个 bug，追下去发现**根因其实是同一类问题：元素脱离了变量/定位的作用域**。

### bug1：新建按钮的子菜单悬停时透明

`.caldav-add-menu` 的样式里，背景色写的是 `background: var(--caldav-bg)`（**无 fallback**），悬停底色是 `color-mix(in srgb, var(--caldav-accent) 10%, var(--caldav-bg))`。

而这个菜单是 `document.body.appendChild(menu)` 挂到 body 下的 —— **不在 `.caldav-root` 之内**，拿不到在那里声明的 `--caldav-*` 变量。于是：

- `var(--caldav-bg)` 解析为空 → 背景透明
- `color-mix()` 含空变量 → **整条声明被丢弃** → 悬停底色消失，能看见背后内容

> 对照之下 `.caldav-ctxmenu` 写的是 `var(--caldav-bg, #fff)`，有 fallback 所以没事 ——
> 说明作者当时想到了浮层挂 body 的场景，只是 `add-menu` 漏了。

**修复**：为所有挂 body 的浮层（`.caldav-add-menu` / `.caldav-ctxmenu` / `.caldav-reminder-layer`）补一份 `--caldav-*` 变量声明，并给菜单容器与悬停底色补上 fallback 作双保险。

### bug2：日历视图右键菜单出现在右侧很远的地方

`.caldav-ctxmenu` 用 `position: fixed`，但它渲染在 `.caldav-root` **内部**（是面板模板里的元素）。而 **Obsidian 的视图容器带 `contain`**（paint / layout）—— 这会让容器成为 `fixed` 元素的**包含块**。

后果：`ev.clientX / clientY` 是**视口坐标**，却被当作**相对容器的坐标**，菜单整体右移了一个「左侧边栏宽度」，看起来跑到很远的地方。

**修复**：`showCtxMenu` 里先把菜单 `appendChild` 到 `document.body`，恢复以视口为参照（与 `add-menu` 的做法一致）。它的点击监听本就绑在元素自身（`on(ctxMenu, "click", ...)`），移动元素不影响。同时在 `destroy` 里补了清理，否则 `root.innerHTML = ""` 清不掉它、重载后会留下孤儿节点。

### 附带修复：`--d-*` 变量 75 处引用、0 处定义

排查时顺手发现：源码里有 **75 处**引用 `--d-accent` / `--d-border` / `--d-input-hover` 等，但**全文件没有一处定义**（应是早期版本的前缀，后来统一成 `--caldav-*` 时漏改）。未定义的变量会让所在声明整条失效，相关属性静默不生效。

**① 一个映射 + 一个函数**

const VIEW_DEFAULT_FILTER: Record<ViewMode, DockFilter | null> = {

1. Dock 初始化（初次进入）
2. 主面板切换视图（监听既有的 `VIEW_CHANGE_EVENT`）
3. 再次单击已选中的格子（新增 `DOCK_RESET_EVENT`）

日视图特殊：`focusDate = getCursor()`，即直接聚焦主面板当前所在的那一天，而不是给一个笼统的预设筛选。

| 事件 | 方向 | 触发 |
| --- | --- | --- |
| `FOCUS_DATE_EVENT`（既有） | 主面板 → Dock | 单击格子 / 条目 |
| `DOCK_RESET_EVENT`（新增） | 主面板 → Dock | **再次**单击已选中的格子 |

**③ `DockPanelOpts` 增两个 getter**

`getViewMode()` / `getCursor()` —— Dock 需要知道主面板当前在哪个视图、哪一天，才能决定默认筛选。用窄接口而非直接传整个 `PanelCtx`。

### 顺带修正：`undone` 的语义

原实现是 `isTodo && !isDone` —— **只筛待办，不含日程**，与「所有未完成」的预期不符（用户明确要求包含"当前时间之后的日程"）。

改为：

```ts
case "undone":
  return isTodo ? !isDone : !ended;
```

`ended` 按**结束时间**与当前时刻比较：进行中的日程保留，只有真正结束的才隐藏。

## 二十、修复：点某日却匹配出大量无关条目（2026-10-03）

**症状**：月视图中点击 2026-10-09 的格子，右侧栏看起来「没显示当天的条目」。

### 排查过程

先查数据（`data.json`）—— **当天确实有 1 条待办**（09:00 那条），所以不是数据问题。

再写临时诊断脚本，用真实数据跑 `matchesDate` 的逻辑，结果：

```
matchesDate("2026-10-09") 命中 45 条
  [event] 2026-09-28T10:00 测试2
  [event] 2026-07-04T07:00 诺诺补牙
  [event] 2026-08-08T10:55 工行额度
  …          ← 全是别的日期的
```

命中 45 条、当日只有 1 条 → **问题不是「没显示」，而是「显示得太多」**：真正那天的那条混在几十条无关日程里，根本看不出来。

### 根因

`core/ics.ts` 的 `expandRepeats`：

```ts
export function expandRepeats(item, rangeStartMs, rangeEndMs) {
  if (!item.rrule || !item.start) return [item.start];   // ← 没有 rrule 就直接返回自身，完全不看窗口
  ...
}
```

所以 `occurrencesInRange(item, 窗口)` 对**普通事件**恒返回它自己的开始时间，**窗口参数形同虚设**（只对重复事件生效）。

而我写的 `matchesDate` 用 `occ.length > 0` 判定命中 —— 于是**所有无重复规则的日程都算命中**。

### 修复

```ts
// 改前：只看展开结果非空
return occ.length > 0;

// 改后：逐个比对日期前缀
return occ.some((s) => !!s && s.slice(0, 10) === date);
```

修复后同一测试：**45 条 → 1 条**，正是当天那条待办。另交叉验证 2026-09-28（按 start 有 7 条）：命中 3 条事件 + 3 条待办按其**到期日**归到 9-29、1 条待办无到期日 —— 逐条核对全部合理，无反向漏匹配。

### 旁证：原作者清楚这个特性

`main.ts` 的 `insertTodayToDiary` 同样调用了这两个函数，但它在循环里做了**二次判断**：

```ts
const ms = parseLocalStamp(occ).getTime();
if (!Number.isFinite(ms) || ms < startMs || ms >= endMs) continue;   // ← 自己再判一次落点
```

所以日记功能一直是对的。是我这次新写 `matchesDate` 时漏了这一层。

> **要记住的口径**：`occurrencesInRange` / `todoDueOccurrences` 的「窗口」参数**只对重复规则生效**，对普通条目无效。**调用方必须自己再判断一次落点。** 任何新的调用点都要注意这条 —— 否则会得到「匹配出全部条目」这种看似列表正常、实则完全错误的结果。

## 二十一、交互再分配：双击空白处开关右侧栏（2026-10-03）

| 操作 | 原行为 | 新行为 |
| --- | --- | --- |
| **双击**日历空白处 | 弹出新建菜单 | **显示 / 隐藏右侧栏** |
| **右键**日历空白处 | —— | **弹出新建菜单** |
| **单击**日期单元格 | 显示右侧栏 + 聚焦该日 | **取消**（不再联动右侧栏） |
| 单击条目 | 聚焦所在日期 | 取消 |
| 双击条目 | 打开编辑器 | 不变 |

### 双击的三态循环

用户定义的规则落到实现上是一个三态循环：

| 当前状态 | 双击后 |
| --- | --- |
| ① 右侧栏关闭 | 打开，并切到「所有未完成」 |
| ② 已打开，但不是「所有未完成」 | 切到「所有未完成」（**不**隐藏） |
| ③ 已打开，且正是「所有未完成」 | 隐藏 |

②③ 的区分靠 **Dock 自报状态**（`isDefaultState()`），而不是在入口侧另记一份 —— 用户可能在下拉里手动切过筛选，入口无从得知。为此 `renderDockPanel` 的返回值扩了一个 `isDefaultState: () => boolean`，由 `CalDavDockView.isDefaultState()` 透传给入口。

### 实现要点

**① 新建菜单从「双击」搬到「右键」**

原先散落在 `view-month.ts` 与 `view-week.ts` 各自的 `dblclick` 监听里。现统一提到 `panel.ts` 的容器委托（`contextmenu` 分支），月 / 周 / 年三套视图共用一份逻辑，不必各写一遍。

周视图「按点击纵向位置取整到 30 分钟」的那段计算也一并搬了过来（`startStampForCell`）—— 它原先依赖 `view-week` 里闭包持有的 `col` 元素，改到委托后从事件目标反查。

**② 空白处的判定**

```ts
function blankDayCell(t: HTMLElement): HTMLElement | null {
  if (t.closest("[data-open]")) return null;      // 点在条目上 → 不是空白处
  const cell = t.closest("[data-day]");
  return cell && app.contains(cell) && cell.dataset.day ? cell : null;
}
```

`contextmenu` 现在先判条目、再判空白格，两条分支互斥：条目上右键仍是原有的编辑 / 删除菜单，空白处才是新建菜单。

**③ 一并删除的**

- 选中格高亮（`selectedDay` / `markSelectedDay` / `applySelectedDay`）—— 它本是为配合「单击聚焦」而加的，单击联动取消后失去语义。CSS 里的 `[data-day].is-selected` 规则**保留未删**，日后要恢复可直接用。
- `DOCK_RESET_EVENT`（原「再次单击已选中格子 → 回到默认」）—— 触发路径没了。
- 单击聚焦（`notifyFocusDate` 的调用点）—— 事件定义与 Dock 侧监听保留，作为日后「从别处定位到某日」的通道。

**④ 新增两个事件**

| 事件 | 方向 | 用途 |
| --- | --- | --- |
| `TOGGLE_DOCK_EVENT` | 面板 → 入口 | 双击空白处 |
| `DOCK_ALL_UNDONE_EVENT` | 入口 → Dock | 强制切到「所有未完成」，而非按视图套默认 |

之所以要 `DOCK_ALL_UNDONE_EVENT` 而不是复用 `VIEW_CHANGE_EVENT`：后者按当前视图套默认筛选（月→所有未完成、周→本周任务），而双击要求的是一律落到「所有未完成」。

### 修正：单击联动恢复（同日）

上一轮把「单击格子 / 条目」的响应**整个删掉**了 —— 那是把「取消单击**自动打开**右侧栏」理解成了「取消单击联动」，属于过度执行。

正确的分工是：**单击管内容，双击管开关**。

| 操作 | 职责 |
| --- | --- |
| 单击格子 / 条目 | 只改右侧栏**内容**（列出该日清单）；右侧栏若关着，事件没有接收者，自然无效果 |
| 双击空白处 | **独占**右侧栏的开关 |

两者不冲突的原因：双击空白处的第一下（`click` 且 `detail === 1`）只改内容，第二下（`detail === 2`）才真正开关。所以右侧栏关闭时双击空白处 —— 第一下无副作用（没人接收），第二下直接打开并落到「所有未完成」，行为干净。

> 这轮也暴露了一个沟通教训：用户说「某某功能取消」时，要分清取消的是**触发方式**（单击不再负责打开）还是**功能本身**（单击不再有任何作用）。改动前若拿不准，问一句比猜一次便宜。

| 双击单元格 | 右侧栏关闭 | 打开右侧栏 + 切到「所有未完成」 |
| 双击单元格 | 已打开，且为「所有未完成」 | 切到「**单元格日期所在月（月视图时）/ 周（周视图时）**」清单（下拉内显示该日期所在月），**不关闭**右侧栏 |

| 右击条目 | | 弹出编辑或删除菜单 |
| 右击单元格 | | 弹出新建菜单 |

### 与既有实现的三处差异（本轮修正）

| # | 原实现 | 应为 |
| --- | --- | --- |
| 1 | 单击只是「再次聚焦该日」 | 单击是**切换**：已聚焦该日 → **取消聚焦并恢复之前显示的内容** |
| 2 | 双击中间态切回「所有未完成」 | 中间态应切到**该日期所在的月 / 周**清单 |
| 3 | 聚焦粒度只有「日」 | 需要「日 / 月 / 周」三种粒度 |

### 实现

**① 状态模型**

```ts
export type FocusScope = "day" | "month" | "week";
let focusDate: string | null = null;      // 聚焦锚点
let focusScope: FocusScope = "day";
let beforeFocusFilter: DockFilter | null = null;   // 进入聚焦前的筛选，取消时恢复
```

`beforeFocusFilter` 是第 1 条差异的关键：表格要求「取消聚焦后**恢复之前显示内容**」，所以在进入聚焦前必须先记一份当前筛选。从 A 日切到 B 日时**不覆盖**这份记录（否则恢复的就不是"之前"了）。

**② 匹配逻辑**

`matchesDate(date)` 泛化为 `matchesRange(from, to)` + `matchesFocus()`：

```ts
function matchesFocus(it: CalItem): boolean {
  if (!focusDate) return false;
  if (focusScope === "month") {
    const ym = focusDate.slice(0, 7);
    return matchesRange(it, ym + "-01", ym + "-31");
  }
  if (focusScope === "week") {
    const ws = startOfWeek(focusDate);
    return matchesRange(it, ws, addDays(ws, 6));
  }
  return matchesRange(it, focusDate, focusDate);
}
```

范围判定仍用**日期前缀比对**（不能沿用 `occurrencesInRange` 的非空判定，原因见 §20）。

**③ 双击带日期**

`notifyToggleDock(date)` 把所点格子的日期一并带给入口；入口按主面板当前视图决定粒度：

```ts
const m = this.mainCtx.viewMode;
const scope: FocusScope = m === "week" || m === "day" ? "week" : "month";
notifyDockScope(date, scope);
```

**④ Dock 自报两个状态**

| 方法 | 含义 | 入口用途 |
| --- | --- | --- |
| `isDefaultState()` | 未聚焦且筛选为「所有未完成」 | 双击时 → 切到月 / 周 |
| `isScopedState()` | 处于聚焦态 | 双击时 → 关闭右侧栏 |

**⑤ 下拉文案按粒度变化**

日 →「10月9日」；月 →「2026 年 10 月」；周 →「10月5日 – 10月11日」。表格里"下拉菜单内显示该日期所在月"指的就是月粒度下的这一显示。

- `renderView()` 末尾重新标记 —— 视图切换会重建 DOM，只标一次的话切视图就丢
- 单击格子：与 Dock 端的聚焦切换**同步** toggle（已聚焦该日 → 取消高亮；否则高亮）
- 双击格子：**主动清除**高亮 —— 双击会改变右侧栏的整体状态（打开 / 换范围 / 关闭），主面板无从预知最终是哪一种，留着边框会与实际聚焦范围对不上

CSS 用 `outline: 2px solid var(--caldav-accent)`：**outline 不参与布局**，格子尺寸不会因选中而跳动；一套 `[data-day].is-selected` 选择器覆盖月 / 周 / 年四种视图（它们的共同点是都带 `data-day`）。

### 续：修复双击循环卡住（单击 / 双击共存的固有陷阱）

**症状**：双击单元格的三态循环走不动 —— 第二态「切到该日所在月 / 周」直接被跳过，一步就到了「关闭右侧栏」。

**根因**：浏览器在双击时**必定先派发一次 `click`，再派发 `dblclick`**。

单击原本是立刻生效的，于是：

```
第一下 click    → Dock：focusDate = 该日（变成聚焦态）
第二下 dblclick → 入口判断：已聚焦？是 → detach（关闭右侧栏）   ← 期望是「切到该日所在月/周」
```

状态机被第一下的副作用**人为推进了一格**，三态循环自然走不通。

**修复**：单击**延后 250ms** 执行；这段时间内若第二下到达，就取消挂起的单击，只按双击处理。

```ts
let clickTimer: ReturnType<typeof setTimeout> | null = null;
function cancelPendingClick(): void { /* clearTimeout */ }

// click：挂起，不立即执行
cancelPendingClick();
clickTimer = setTimeout(() => {
  clickTimer = null;
  /* …toggle 高亮 + notifyFocusDate(day)… */
}, 250);

// dblclick：先撤掉第一下挂起的单击，再走三态
cancelPendingClick();
markSelectedDay(null);
notifyToggleDock(cell.dataset.day!);
```

条目单击也一并加了延迟 —— 双击条目的第一下同样会先把状态改掉（那里原用 `ev.detail >= 2` 区分，但第一下的副作用已经发生了）。

**代价**：单击会有 250ms 延迟。这是单击 / 双击共存于同一元素的**固有代价** —— 浏览器不告诉你是「要点」还是「要双击」，只能等一个双击窗口过去。想彻底消除延迟，就得放弃其中一个手势。

> 这条与 §20 的「`occurrencesInRange` 窗口参数只对重复规则生效」性质相同：都是**调用方默认某件事不会发生，但实际会发生**。前者的假设是"非空即命中"，后者的假设是"click 不会影响 dblclick 的状态判断"。

### 续：第 3 态改为「隐藏整个右侧栏」（表格第三次修订）

表格第二次修订把三处「关闭」统一改成了「**隐藏**」：

| | 上一版 | 本版 |
| --- | --- | --- |
| 第 1 态 | 右侧栏**关闭** | 右侧栏**隐藏** |
| 第 1 态动作 | 打开右侧栏 | 打开右侧栏 |
| 第 3 态 | **关闭**右侧栏 | **隐藏**右侧栏 |

措辞变化是有实义的，不是同义替换：

| 说法 | 实现 | 效果 |
| --- | --- | --- |
| ~~关闭~~ | `leaf.detach()` | 把插件视图**销毁**，标签页消失；再打开要重建 |
| **隐藏** | `rightSplit.collapse()` | 把**整个右侧栏折叠起来**；视图实例保留，再展开时状态还在 |

选后者的两个依据：
1. 字面就是「右侧栏被隐藏」，而不是「某个标签被关掉」；
2. 第 1 态说的是「右侧栏**隐藏** → 打开右侧栏」——「隐藏 ▸ 打开」这一对，正好对应 `collapse` / `expand`。

**实现调整**：

```ts
const rightSplit = workspace.rightSplit;
const isCollapsed = !!rightSplit?.collapsed;

// ① 视图不存在 **或整个右侧栏被折叠** → 展开 + 「所有未完成」
if (leaves.length === 0 || isCollapsed) {
  void this.activateDock().then(() => {
    rightSplit?.expand();
    notifyDockAllUndone();
  });
  return;
}
// ③ …
rightSplit?.collapse();   // 折叠不可用时退回 detach，至少保证能收起
```

注意第 1 态的判断条件多了 `isCollapsed`：视图可能还在（只是被折叠了），这时不能只调 `revealLeaf`，得先把侧栏展开。

`collapse()` / `expand()` 是 Obsidian 的公开 API（`tsc` 直接通过，无需类型断言）。

## 二十三、周视图三处显示修正（2026-10-03）

雄哥反馈的三个视觉问题，根因互不相同。

| 现象 | 根因 |
| --- | --- |
| 选中某天时，标题的框与下方时间轴的框**对不齐** | 滚动条宽度未补偿（下方详述） |
| 当日（紫底圆圈）**超出格子边界** | 表头高度写死 `44px`，内容实际更高 |
| 时间轴起点「00:00」**只显示一半** | 首个整点标签被滚动容器裁掉 |

### ① 表头与时间网格不等宽（对不齐的根因）

结构上，表头在滚动容器**之外**：

```
.cal-wk
  ├ .cal-wk-header      ← 表头（在滚动容器外）
  │   ├ .cal-wk-gutterhead (48px)
  │   └ .cal-wk-days    (grid, repeat(7, 1fr))
  └ .cal-wk-main        ← 纵向滚动容器（overflow-y: auto）
      ├ .cal-wk-gutter  (48px)
      └ .cal-wk-grid    (grid, repeat(7, 1fr))
```

两者都用 `repeat(7, 1fr)`，但**可用宽度不同**：`.cal-wk-main` 出现纵向滚动条时会吃掉右侧十几像素，而表头没有这条滚动条。于是表头每列都比下方宽一点 —— 而且是**越靠右偏差越大**，所以选中周四那一栏时两个框明显错开。

**修复**：JS 侧量出滚动条实际占用宽度，写入 `--wk-sbw`，表头用它补偿右侧内边距。

```ts
const sbw = sc.offsetWidth - sc.clientWidth;   // 滚动条宽（无滚动条时为 0）
if (sbw > 0 && wk) wk.style.setProperty("--wk-sbw", `${sbw}px`);
```

```css
.cal-wk-header { padding-right: var(--wk-sbw, 0px); }
```

不写死数值是因为滚动条宽度随平台与 Obsidian 主题而变（Windows 原生约 15px，自定义主题可能更窄）。

### ② 表头高度自适应

```css
/* 改前：写死高度，而「周几 + 日期数字」两行 + padding 已超出 */
.cal-wk-header { height: 44px; flex: 0 0 44px; }

/* 改后 */
.cal-wk-header { height: auto; min-height: 44px; flex: 0 0 auto; }
```

当日那个圆形标号是 `.cal-wk-num` 上的 `border-radius: 50%` + 强调色底，内容一超高就被挤出格子边界。

### ③ 首个整点标签不再上移

```css
.cal-wk-hour span { position: absolute; top: -7px; }        /* 让标签骑在整点线上居中 */
.cal-wk-hour:first-child span { top: 0; }                   /* 但 00:00 在滚动区顶端，上移会被裁掉一半 */
```

### 续：选中态改为「日头 + 所点小时」两段式

雄哥反馈：周 / 日视图里单击一下就把**整条时间轴**框住，太重了。改为两段：

| 位置 | 高亮 |
| --- | --- |
| 顶部日头（周标题） | 一个框 |
| 所点的那 1 小时 | 另一个框 |

**实现**：

1. **时间轴列不再整列高亮** —— `applySelectedDay()` 里显式跳过 `.cal-wk-col`：

   ```ts
   root.querySelectorAll<HTMLElement>("[data-day]").forEach((c) => {
     if (c.classList.contains("cal-wk-col")) { c.classList.remove("is-selected"); return; }
     // …其余格子照旧
   });
   ```

2. **新增 `selectedHour` 状态**，`hourFromClick()` 按点击的纵向位置换算小时：

   ```ts
   const ratio = (ev.clientY - rect.top) / rect.height;
   return Math.min(23, Math.max(0, Math.floor(ratio * 24)));
   ```

   只在 `.cal-wk-col` 上有意义；月 / 年视图的格子、周视图的日头都不分小时 → `null`。

3. **动态插入高亮块**（`.cal-wk-selected-hour`），绝对定位在对应列内：

   ```ts
   box.style.top = `${(selectedHour / 24) * 100}%`;
   box.style.height = `${100 / 24}%`;
   ```

   用**百分比**而不是 `selectedHour * HOUR_H`，这样与视图里的格子高度常量解耦 —— 以后调时间轴密度不必同步改这里。

4. CSS 上 `pointer-events: none`，否则会挡住底下条目的点击与双击。

月 / 年视图没有小时概念，行为不变（只框住被点的格子）。

### 续：双击与右击的行为互换（表格第四次修订）

| 手势 | 目标 | 上一版 | 本版 |
| --- | --- | --- | --- |
| **双击** | 单元格空白 | 三态循环 | **新建菜单** |
| **右击** | 单元格空白 | 新建菜单 | **三态循环** |
| ~~右击~~ → **双击** | 条目 | 编辑 / 删除菜单 | **编辑菜单** |

注意第三行：除了交换，「条目菜单」的**触发方式**也从右击改成了双击。

### 一个意外的好处：§22 那个坑从根上消失了

三态循环原先挂在**双击**上，而浏览器双击时必定先派发一次 `click` —— 第一下就会把状态推进一格，当时只能靠「单击延后 250ms」绕开（§22）。

换到**右击**之后，`contextmenu` **不会先派发 `click`**，这个干扰自然不存在了。也就是说：这个手势换得比看起来更合理。

### 单击延迟继续保留

双击**条目**（弹编辑菜单）与双击**空白**（弹新建菜单）仍然会有"第一下先把该日聚焦了"的副作用 —— 延迟正好把它们挡掉，所以没去掉。

### 表格未定义的手势

表格这次没给「**右击条目**」任何定义（上一版有）。两可之间选择了**保留**既有的编辑 / 删除菜单：
- 多一个入口不影响表格已定义的手势（右击条目走的是条目分支，右击空白走三态分支，两者互斥）；
- 万一雄哥本意是要腾空这个手势，删掉它只是一行的事。

### 续：双击条目改为直接进入编辑 + 日视图放宽第 3 态（表格第五次修订）

**① 双击条目 → 直接进入编辑**

上一轮我把表格里的「弹出编辑菜单」理解成了「弹出 编辑/删除 的上下文菜单」—— 理解偏了。**它指的是打开编辑器本身**。

雄哥的理由很直接：**编辑器左下角本来就有删除按钮**，再弹一层菜单是多余的。

```ts
// 改前：弹上下文菜单
showCtxMenu(key, ev.clientX, ev.clientY);
// 改后：直接打开编辑器
openEditor(ctx, { item });
```

> 教训：行为表里的「菜单」一词要看上下文。这个项目里 `菜单` 至少有三种指向 ——
> 工具栏的新建浮层、条目的上下文菜单、以及「编辑弹窗」。单看措辞定不下来，得结合产品逻辑
> （这里：编辑器已有删除按钮 ⇒ 再弹菜单没有增量价值）。

**② 第 3 态增加「或者当前为日视图」**

| | 上一版 | 本版 |
| --- | --- | --- |
| 第 3 态条件 | 右侧栏已打开，且清单为「单元格日期所在月 / 周」 | …**或者当前为日视图** |

日视图下不必再走一遍「切到该日所在周」，第二次右击直接收起：

```ts
if (view.isScopedState() || this.mainCtx.viewMode === "day") {
  rightSplit?.collapse();
  return;
}
```

**判断顺序仍是 `isDefaultState` 优先** —— 所以日视图 + 「所有未完成」时，第二击走的是第 2 态（切到该周），第三击才收起，循环依然完整。

**③ 保留的手势**

表格这版仍未定义「**右击条目**」。继续保留既有的编辑 / 删除菜单（右击条目与右击空白走互斥分支，不冲突）；若雄哥本意是要腾空它，删掉只是一行。

## 二十五、修复：点一次「取消」关不掉编辑器（2026-10-03）

**症状**：双击条目弹出编辑对话框后，点一次「取消」没反应，**要点两次**才关得掉。

### 根因：编辑器被打开了两次

两个 Modal 叠在一起 —— 点一次「取消」只关掉上面那个，露出下面那个，所以要点两次。

为什么开了两次：条目的事件处理有**两条路径都在打开编辑器**。

```
click (detail=2) → openEditor   ← 第一个弹窗
dblclick         → openEditor   ← 第二个弹窗
```

`click` 处理器里留着一个 `ev.detail >= 2` 的旧分支 —— 那是更早的实现（用 `detail` 计数判定双击）留下的。后来改成监听 `dblclick` 事件时，**旧分支忘了删**。

> 这是**重构残留**：换了判定方式，但没清掉旧的判断分支。同一件事被两套机制各做了一遍。

### 修复

**① 让职责唯一**：`click` 处理器只管单击，双击一律交给 `dblclick` 处理器。

```ts
// 删掉这个分支
if (ev.detail >= 2) { openEditor(ctx, { item }); }
// 只留单击逻辑（挂 250ms 定时器做聚焦）
```

**② 加一道防线**：`editor.ts` 里记住当前打开的编辑器实例，`onOpen` 时先关掉上一个。

```ts
let activeEditor: EditorModal | null = null;

onOpen(): void {
  if (activeEditor && activeEditor !== this) activeEditor.close();
  activeEditor = this;
  // …
}
onClose(): void {
  if (activeEditor === this) activeEditor = null;
  // …
}
```

之所以专门设防，是因为**这个 bug 的症状具有误导性**：用户看到的是"按钮不灵"，而根因在"弹窗开了两个"，两者之间没有直观联系。若将来某处又引入重复调用，这道防线能让症状消失在源头。

> 附带记一条排查经验：**「要点两次才关掉」几乎是"叠了两个弹窗"的特征症状**。下次再遇到，先数一下开了几个，比盯着关闭按钮的代码看更快。

## 二十六、右击条目 → 右侧栏显示条目详情（2026-10-03）

表格第六版新增两条（行数 9 → 11）：

| 鼠标动作 | 当前状态 | 执行操作 |
| --- | --- | --- |
| **右击条目** | 右侧栏隐藏 | 打开右侧栏，显示该条目的所有详细信息 |
| **右击条目** | 右侧栏已打开 | 隐藏右侧栏 |

这是**新功能**，不是既有行为的调整 —— Dock 此前只有「清单」一种形态，现在需要多一个「详情模式」。

### 实现

**① Dock 侧：新增 `detailKey` 状态**

非空时列表区整块让给详情卡片：

```ts
function renderDockList(): void {
  if (destroyed) return;
  if (detailKey) { renderItemDetail(); return; }   // 详情模式
  // …常规清单
}
```

`renderItemDetail()` 输出这些字段（取自 `CalItem`）：

| 类型 | 待办任务 / 日程 |
| --- | --- |
| 日历 | 该条目所属日历名 |
| 时间 | 日程 → 开始 / 结束（+ 全天）；待办 → 到期 |
| 状态 | 待办 → 已完成（含完成时间）/ 未完成；优先级 |
| 地点 / 分类 / 重复 / 提醒 / 描述 / 创建时间 | 有值才显示 |

**② 加了一个表格没定义的「← 返回列表」**

表格只规定了"右击条目怎么打开详情"，没说怎么退出。若不提供出口，用户看完详情就回不到清单了（除非再右击一次收起整个右侧栏，但那不符合直觉）。故在详情卡片顶部放了一个返回按钮。

**③ 入口侧：两态（不同于单元格的三态）**

```ts
private toggleDockItem(key: string): void {
  // ① 隐藏（视图不存在 / 已折叠）→ 展开 + 显示该条目详情
  // ② 已打开 → 收起
}
```

它不碰清单筛选 —— 打开时右侧栏直接进详情模式。

**④ 触摸端长按同步改掉**

长按是桌面右击的等价操作，原先弹「编辑 / 删除」菜单，现一并改为详情。

### 顺带：`showCtxMenu` 失去了最后一个调用者

右键条目与触摸长按都改走详情后，条目上下文菜单（编辑 / 删除）**不再有任何入口**，`showCtxMenu` 成为死代码。

选择**保留**而不是删除：删它要连带清理模板里的 `.caldav-ctxmenu` DOM、`hideCtxMenu` / `ctxMenuKey` / `ctxDelBtn` / `resetCtxDelete` 等一整套状态，改动面大且容易漏；而它已经不再被触发，留着无副作用。将来若需要条目菜单，这套现成的可以复用。

（删除功能并未丢失：双击条目 → 编辑器 → 左下角有删除按钮。）
